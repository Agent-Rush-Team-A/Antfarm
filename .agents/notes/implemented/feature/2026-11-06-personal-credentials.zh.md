# Agent Note: 个人凭证归属请求发起人

Status: implemented

[English](2026-11-06-personal-credentials.md) | 中文

## 问题

全局凭证 provider 为所有 Harness 消费者解析名称，并回退到部署环境变量。向普通账号开放写入权限会允许一个账号替换其他账号的凭证或推理密钥。工作区成员关系无法标识个人凭证的所有者，也无法标识后续外部服务请求的发起人。

## 决策

个人凭证插件拥有独立的加密存储域和浏览器 API。每次操作从已认证 invocation 获取账号，在操作自身检查记录归属，并拒绝 owner 或缺失用户身份。[Host README](../../../../packages/api/user-credentials/README.zh.md)负责说明存储与失败语义。

因为存储域事件携带记录值，所以凭证在写入前加密。AES-GCM 将密文与账号、记录 ID 和版本绑定。主密钥在工作区挂载目录外显式初始化，缺失时不会重新生成。读取响应仅返回安全元数据。后端保存检查验证已授权的解密，不释放明文，也不表示外部服务授权有效。

## 考虑过的替代方案

**开放现有凭证命名空间。** 扁平引用与环境变量回退属于整个部署。向普通用户开放会改变全局 provider 行为，无法保证个人归属。

**给全局名称加用户 ID 前缀。** 命名约定不能授权访问，任意全局存储消费者仍能解析这些值。独立存储让隔离成为实现本身的属性。

## 影响

保存检查仍在本地执行，不提供通用外部请求代理，工作区共享不会授予凭证权限。密钥轮换需要显式迁移，丢失主密钥会导致密文不可用。名称仍是用户提供的非秘密元数据。

## 验证

Host 测试覆盖两个账号的同名凭证、跨账号变更与解密检查、密文归属绑定、重启可读性、主密钥错误、数量限制和请求撤销。
